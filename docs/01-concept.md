# 01. 設計思想と「作業手順開発」の進め方

## 1. 作業手順開発とは

**作業手順開発（手順駆動開発）** は、「作りたい機能」ではなく「**人間が実際に行う作業の手順**」を最初に書き起こし、その手順を最短で実行可能にする機能だけを実装していく開発アプローチです。

```
①作業手順を書く ──▶ ②手順の各ステップに必要なコマンドを列挙 ──▶ ③コマンドが操作する状態(データ)を定義
        ▲                                                                       │
        │                                                                       ▼
⑥手順を実際に流して検証 ◀── ⑤最小実装 ◀── ④コマンドの入出力・失敗パターンを固定
```

### なぜこのプロジェクトに適しているか

1. **操作主体が AI である** — AI は「ボタンを探す」のではなく「手順をコマンドに翻訳する」。手順が明文化されていれば、そのまま AI のプロンプト／ツール定義になる。
2. **CLI は手順そのもの** — GUI の自由度がないぶん、コマンドの並び＝作業手順。手順が先にあれば必要なコマンドは自然に決まり、不要なコマンドを作らずに済む。
3. **検証が自動化しやすい** — 各作業手順はそのままシェルスクリプトとして E2E テストになる。

### 進め方の原則

| 原則 | 説明 |
|------|------|
| 手順が仕様 | `03-workflows.md` の手順 ID（`W-xx`）を起点に、コマンド・データ・ffmpeg 変換を紐付ける（トレーサビリティ） |
| ステップ 1 つ = コマンド 1 つ | 1 ステップを実行するのに複数コマンドが必要ならサブコマンドや複合コマンドを検討する。逆に 1 コマンドで複数ステップを隠さない |
| 失敗手順も書く | 「素材が見つからない」「クリップが重なる」などの失敗時に AI が次に何をすべきかも手順に含める |
| まず素朴に、ffmpeg 1 回で | 初期は「タイムライン → 1 本の `ffmpeg -filter_complex`」で全てを賄い、性能問題が出た段階でセグメント分割・キャッシュを導入する |
| 確認は Web、判断は人間、操作は AI | プレビューは Web が見せる。良し悪しを判断するのは人間。その結果をプロンプトで AI に伝え、AI がコマンドを打つ |

## 2. 全体像（役割分担）

```
┌──────────┐  自然言語      ┌──────────┐  montash ...       ┌────────────────────┐
│  人間     │ ─────────────▶│   AI     │ ────────────────▶ │  montash CLI        │
│ (判断)    │ ◀───────────── │ (翻訳)   │ ◀──────────────── │  (状態操作)          │
└──────────┘  結果報告       └──────────┘  JSON 出力/エラー  └─────────┬──────────┘
      ▲                                                              │ 読み書き
      │ 目視確認・履歴移動・素材管理                                     ▼
┌──────────┐  HTTP/WS       ┌──────────────┐  POST /api/cli  ┌────────────────────┐
│ ブラウザ  │ ◀────────────▶ │ montash serve │ ──(montash …)──▶ │  project.json      │
│ (Web UI)  │                │              │ ◀── 監視 ────── │  + .montash/       │
└──────────┘                └──────────────┘                └─────────┬──────────┘
                                                                      │ montash render
                                                                      ▼
                                                            ┌────────────────────┐
                                                            │  ffmpeg / ffprobe   │
                                                            └────────────────────┘
```

- **人間**: 素材を用意し、指示を出し、プレビューを見て判断する。Web の History で過去の状態を見比べ、素材を整理する。
- **AI**: 指示を `montash` コマンド列に翻訳し、実行結果（JSON）を読んで次の手を決め、作業単位をコミットとして記録する。
- **montash CLI**: `project.json` を検証しながら更新し、履歴（op）を記録し、ffmpeg を呼び出す唯一の場所。
- **Web UI**: `project.json`・履歴・生成済みプロキシを読んで可視化する。Web からの操作（履歴移動・素材管理）は **すべて `montash` コマンドの発行**として実行され、`actor: web` で履歴に残る（06 章）。

## 3. 設計原則（詳細）

### 3.1 状態は 1 か所に（Single Source of Truth）

- 編集状態は `project.json` のみ。CLI・Web・render すべてがこれを読む。
- 派生物（プロキシ、サムネイル、probe、プレビュー、レンダーキャッシュ）は `.montash/cache/` `.montash/preview/` 配下に置き、**いつ削除しても再生成できる**。履歴（`.montash/history/`）と採番カウンタ（`.montash/ids.json`）は派生物ではなく、削除すると追跡性が失われる。

### 3.2 非破壊・冪等

- アセットは読み取り専用。トリムもエフェクトも `project.json` 上の記述に留める。
- 同じコマンドを同じ状態に対して 2 回実行しても結果が変わらない（ID を指定した操作は上書き、追加系は重複を検出して警告）。

### 3.3 AI にやさしい入出力

- すべてのコマンドが `--json` で構造化出力を返す。
- エラーは「何が」「なぜ」「どう直せるか（`hint`）」を含む。
- `--dry-run` で実際に実行される変更・ffmpeg コマンドを事前確認できる。
- `montash schema` / `montash help --json` でコマンド定義を機械可読に取得でき、AI のツール定義として利用できる。

### 3.4 時間の扱い

- プロジェクトの **fps と解像度が基準単位**。内部の時間は **fps 基準の整数フレーム**（音声のサブフレーム補正のみ整数サンプル）で保持し、浮動小数の比較を行わない（05 章 §2、ADR-09）。
- 入力は `12.5` / `00:00:12.500` / `f:375`（フレーム）を受け付け、秒指定は最寄りフレームに丸めて `W_SNAPPED` で採用値を返す。
- 秒への変換は表示と ffmpeg 境界でのみ行い、ffmpeg にも可能な限りフレーム数・サンプル数で渡す（07 章）。

### 3.5 段階的な正確さ

- Web プレビューは「プロキシ品質」で十分。正確な色・音は最終レンダーで確認する。
- ただしタイミング（カット位置・トランジション長）はプレビューでも正確であること。

## 4. 作業手順開発のサイクル（このリポジトリでの実践）

1. `03-workflows.md` に手順を追加／更新する（ID を振る）。
2. 手順の各ステップから必要なコマンドを `04-cli-spec.md` に起こす（`W-xx` を参照として記載）。
3. コマンドが読み書きするデータを `05-project-format.md` に追加する。
4. ffmpeg で実現する部分を `07-ffmpeg-mapping.md` に対応表として書く。
5. `09-roadmap.md` のトレーサビリティ表を更新する。
6. 手順をそのままシェルスクリプト化し `tests/workflows/W-xx.sh` として E2E テストにする。

この順序を守ることで、「手順にないコマンド」「コマンドにないデータ」を作らないようにします。
